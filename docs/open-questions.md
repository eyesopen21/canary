## Open questions about the agents

The hook is only as strong as the agent that runs it. These questions decide what the README may promise.

Synthetic local harness note (2026-11-22): `tests/mcp-contract.test.ts` drives the built prototype over its own stdio JSON-RPC endpoint with synthetic marker fixtures. It verifies the prototype's local contract only; it is **not** live-agent evidence. No Claude Code or Codex session was run for this pass, so Q21, Q23 and Q26 remain Open.

| Q21 | What happens on the first command with the opt-in `mcp_tool` hooks in live Claude Code and Codex sessions? | Claude Code skips launch-time `SessionStart` MCP hooks, then waits for a connecting server on blocking `PreToolUse` events, bounded by `MCP_TIMEOUT` and the hook `timeout`; `onFailure: "block"` for MCP hooks requires v2.1.328 [S1] (re-verified 2026-11-22). Claude Code reads the tool's text content like command-hook stdout, and an `isError: true` result is a non-blocking error unless `onFailure` is set [S1]. Codex hooks use an already-connected server, do not start or reconnect one, and missing servers, unavailable tools, errors and timeouts do not block [S8] (re-verified 2026-11-22). `tests/mcp-contract.test.ts` checks the prototype's own first-call and unavailable-tool paths, but not a host. | Open. No live Claude Code or Codex session was run. Record exact agent versions, whether the server is connected before the first tool call, and the resulting allow/block behavior. |
| Q22 | Can Canary ensure MCP hook inputs cannot carry secrets while still evaluating the current shell policy? | The tool's advertised schema has exactly four properties: `agent` (enum `claude-code`/`codex`), `tool_name`, `command` (max 32,768 chars) and `cwd` (max 4,096 chars), all four required, `additionalProperties: false` (`src/mcp-hook/server.ts:13-23`, confirmed by the local harness). Both host templates interpolate `${tool_input.command}` and `${cwd}` from the hook event. Claude Code substitutes `${path}` strings and Codex keeps a placeholder's JSON type when it fills a whole value; neither documents pre-call redaction [S1][S8]. **Secret-bearing fields:** `command` is arbitrary shell text, so a credential literal typed in a shell command reaches Canary intact; `cwd` is checked only for type and length, so its content is unconstrained too, though it is a path rather than shell text. `agent` and `tool_name` are constrained to fixed values and cannot carry arbitrary text. **Where processed:** `evaluateTool()` copies `command` into `tool_input.command` and `cwd` into the event, then calls `hookEvaluator()` and the agent adapters (`src/mcp-hook/server.ts:52-79`); `hookEvaluator()` also reads fixed environment-variable names (`src/cli/hook.ts:17-25`). **Protection that exists:** extra fields rejected, size limits, no logging or echo of raw input, fixed generic invalid-input messages, and ADR-0003 sanitization of adapter messages (synthetic marker tests pass locally). A sanitized git remote name may still appear in a block message, and the raw `command` still crosses the local stdio boundary into Canary. Hosts SHOULD show tool inputs to the user before calling a server, and hosts must obtain consent before exposing user data to servers [S5][S6][S8]. | Open. No pre-call redaction exists, and no live session showed what a host displays. This is a shipping blocker for any requirement that MCP inputs contain no secret-capable data. Find a safe host-side transformation or keep the command-hook path. Local marker tests are not proof that secrets never reach the server. |
| Q23 | Do Claude Code and Codex keep the stdio server alive for repeated hook calls, and can the model invoke its tool directly outside hooks? | The docs say MCP tool hooks use an existing connection and run synchronously; Codex explicitly does not start or reconnect servers [S1][S8]. The synthetic harness confirms that one prototype process serves repeated calls and that a fresh process handles its first call, but that is the harness's own lifecycle, not either host's. `npm run bench:mcp` is likewise a local timing harness. | Open. No live session was run. Verify connection lifetime, direct-call exposure, restart behavior, and shutdown in live sessions before shipping. |
| Q26 | Does the prototype stdio server conform to MCP version 2026-07-28 [S5][S6][S7] and to each host's client? | Re-checked against primary sources on 2026-11-22. The catalogued 2026-07-28 revision has **no `initialize` handshake**: every request carries version, identity and capabilities in per-request `_meta`, servers `MUST` implement `server/discover`, and an unsupported version returns `-32022 UnsupportedProtocolVersionError` with a supported-version list; `initialize` is a legacy (2025-11-25 and earlier) method and lacks the required `_meta` [S5, *Versioning and Compatibility*]. The prototype instead negotiates through `initialize`, accepts `2026-07-28`, `2025-11-25` and `2025-06-18`, records `notifications/initialized` without requiring it before `tools/call`, and silently defaults an unknown version to `2026-07-28` instead of returning `-32022` (`src/mcp-hook/server.ts:82-111`; confirmed by the synthetic harness). `npm run bench:mcp` exercises only that legacy-style `initialize` exchange and repeated `tools/call` timing. Two earlier notes were corrected by [S6]: `resultType: "complete"` is part of the catalogued 2026-07-28 `tools/list` and `tools/call` response shape, so its presence is not itself a deviation; and the required `tools` capability is declared. S6 also requires servers to validate all tool inputs and sanitize outputs, which the prototype does locally. | Open. The prototype implements legacy handshake semantics, not the catalogued modern 2026-07-28 semantics; no conformance check against a live host was run. Reconcile the version set, `_meta`/`server/discover` handling and handshake behavior with the cited specification, then record exact client versions in the live check [Q21][Q23]. |
